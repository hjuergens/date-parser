Eight parsers, one date language

The language

Small enough for every tool, rich enough to show their differences: three date notations, periods, lists and ranges.

06/09/2015 + 1W - 2D2015-06-14 (US notation, left to right)
2015-06-09, 1.1.2000 + 1Y2015-06-09, 2001-01-01
(2015-01-15 : 1Q : 2015-12-31)2015-01-15, -04-15, -07-15, -10-15
 
schedule = range | expr { "," expr } .
range    = "(" expr ":" period ":" expr ")" .
expr     = date { ("+" | "-") period } .
date     = NUM ( "-" NUM "-" NUM       (* ISO    *)
               | "." NUM "." NUM       (* German *)
               | "/" NUM "/" NUM ) .   (* US     *)
period   = NUM ( "D" | "W" | "M"
               | "Q" | "Y" ) .

Every decision is LL(1): after the first number, the separator selects the notation; after a complete date, + or - starts a period. Periods follow java.time: months first, with the day clamped to the end of the month (2016-01-31 + 1M is 2016-02-29), then days.

ALL(*) · adaptive LLJava DateSchedule.g4 ↗ 
// periods are applied from left to right
expr returns [LocalDate value]
    : date                          { $value = $date.value; }
      ( '+' period                  { $value = $value.plus($period.value); }
      | '-' period                  { $value = $value.minus($period.value); }
      )*
    ;

date returns [LocalDate value]
    : y=NUM '-' m=NUM '-' d=NUM     { $value = LocalDate.of($y.int, $m.int, $d.int); }  // ISO
    | d=NUM '.' m=NUM '.' y=NUM     { $value = LocalDate.of($y.int, $m.int, $d.int); }  // German
    | m=NUM '/' d=NUM '/' y=NUM     { $value = LocalDate.of($y.int, $m.int, $d.int); }  // US
    ;

Pitfall. $start is reserved (the rule's first token), so the range labels are first/last.

Recursive descent with backtrackingScala 2.13 ScheduleParsers.scala ↗ 
def date: Parser[LocalDate] = number ~ (
    ("-" ~> number) ~ ("-" ~> number) ^^ { case m ~ d => (y: Int) => LocalDate.of(y, m, d) }  // ISO
  | ("." ~> number) ~ ("." ~> number) ^^ { case m ~ y => (d: Int) => LocalDate.of(y, m, d) }  // German
  | ("/" ~> number) ~ ("/" ~> number) ^^ { case d ~ y => (m: Int) => LocalDate.of(y, m, d) }  // US
  ) ^^ { case first ~ toDate => toDate(first) }

def expr: Parser[LocalDate] = date ~ rep(("+" | "-") ~ period) ^^ {
  case start ~ shifts => shifts.foldLeft(start) {
    case (d, "+" ~ p) => d.plus(p)
    case (d, _ ~ p) => d.minus(p)
  }
}

Pitfall. None: the grammar is ordinary Scala code, there is no generator step.

LALR(1)Java schedule.cup ↗ 
/* periods are applied from left to right */
expr ::= date:d                     {: RESULT = d; :}
       | expr:e PLUS period:p       {: RESULT = e.plus(p); :}
       | expr:e MINUS period:p      {: RESULT = e.minus(p); :}
       ;

date ::= NUM:y MINUS NUM:m MINUS NUM:d      {: RESULT = LocalDate.of(y, m, d); :}   /* ISO */
       | NUM:d DOT NUM:m DOT NUM:y          {: RESULT = LocalDate.of(y, m, d); :}   /* German */
       | NUM:m SLASH NUM:d SLASH NUM:y      {: RESULT = LocalDate.of(y, m, d); :}   /* US */
       ;

Pitfall. In the JFlex spec, %cupsym must come before %cup, or the EOF action refers to sym.

What the comparison shows

  • Top-down needs right recursion, bottom-up likes left recursion.

    The LL tools and Peggy write date { ("+" | "-") period } as a loop. CUP and Bison write expr '+' period, which is natural for LALR(1).

  • Separating syntax from semantics is a choice.

    SableCC's grammar contains no code at all; a separate tree walker computes the dates. Every other tool interleaves actions with the rules.

  • Error recovery has consequences.

    Coco/R recovers and keeps executing actions on incomplete input, so the actions must tolerate it. ANTLR needs a bail strategy to stop at the first error.

  • Ordered choice is not alternation.

    PEG tries the alternatives in order and commits to the first match. Here this is harmless because the separators differ, but it's the main semantic difference to the generated LL and LR parsers.

  • The library matters as much as the parser.

    In JavaScript, about 35 lines reproduce java.time's month arithmetic. The end-of-month cases in the test file exist to catch differences.

  • A shared test file keeps everyone honest.

    Every module reads examples/schedule.txt. Several tool-specific pitfalls, listed in the tabs above, surfaced only because the same cases had to pass everywhere.

Run it yourself

You need JDK 17 and Maven 3.9. Bison is optional: without it the Bison module builds empty. The Peggy module downloads its own Node.js.

git clone https://github.com/hjuergens/date-parser.git
cd date-parser
mvn clean verify                      # all modules
mvn -pl date-rule-coco test           # one module
